## 1. 目的

OneMoreCoffee に、フレンド同士で楽しむソーシャル機能を追加する。
機能の柱は次の 2 つである。

- **訪問店舗数ランキング**：フレンド間で制覇の進み具合を競う
- **アクティビティフィード**：フレンドが訪問した店舗が時系列で流れる

この設計は 2 つの目的を兼ねる。
1 つは、実在する数人の友人と実際に使うための実装検討である。
もう 1 つは、DroidKaigi 2026 セッション「個人開発という実験場」の素材である。
アイディアから設計、実装に至る過程そのものが、自由 2（アイディアを実装に運ぶ自由）と自由 4（自分のためのアプリを作る自由）の実例になる（§8）。

## 2. 前提と制約

### 2.1 本体設計から引き継ぐ制約

本体設計書は次の方針を定めており、本機能はこれらとの整合を取る必要がある。

- プライバシー方針（本体設計書 §3.3）：訪問履歴と店舗データはすべて端末ローカルに保持し、外部送信は行わない
- 公開配布不可（同 §3.1）：店舗マスタの規約上、Play Store 等での配布は行わない
- 店舗マスタの再配布禁止（同 §3.1）：取得した店舗データを他者に配布しない
- 端末間同期はスコープ外（同 §2.3）：個人利用前提を理由とした除外であり、本機能はこの前提そのものを変更する

前 3 項への対応はそれぞれ §4.6、§7（配布）、§4.6 で述べる。

### 2.2 利用者の規模

公開配布ができないため、フレンドになれるのは APK を直接受け取れる相手に限られる。
実際に一緒にスターバックス巡りをする友人が数人おり、この数人が想定利用者のすべてである。

したがって、一般的な SNS に必要なスケーラビリティ、見知らぬ利用者への防御、チート対策は設計対象にしない。
全員が信頼できる友人であるという前提は、単なる割り切りではなく、アーキテクチャを単純化する材料として積極的に利用する（§5.2 のランキング自己申告方式、§5.3 の招待コード検証の省略）。

### 2.3 設計判断の記録

設計に先立つヒアリングで、次を確定した。

- 目的：発表素材と実装の両方（実装を視野に入れた現実的な検討）
- 想定利用者：実在する友人数人
- つながりモデル：グループ型（§4.1 のリーグ）
- 共有粒度：店舗名も時刻もそのまま共有する（検討の経緯は §4.5）
- インフラ制約：なし（3 方式を比較して決定）

## 3. 実現方式の検討

### 3.1 共通原則：サーバー上のデータはすべて導出データ

どの方式を採る場合も、次の原則を置く。

**端末の Room データベースが唯一の原本であり、サーバーには Room から導出した共有用データだけを置く。**

この原則から次の性質が得られる。

- サーバー側のデータが全損しても、手元の訪問記録は無傷である。再送すれば復元できる
- 機種変更や再インストールで認証情報を失っても、原本は失われない（§5.5）
- バックエンド実装を将来差し替える場合も、データ移行は「再送」で済む（§3.3 の移行経路）
- 退会はサーバー側の削除だけで完結する

本体設計のローカルファースト方針を弱めるのではなく、原本はローカルに置いたまま、共有用の導出レイヤーを外側に 1 枚足す構図である。

### 3.2 検討した 3 方式

#### 案 A: Firebase（Firestore + Anonymous Auth）

Firestore にリーグ、メンバー統計、アクティビティを置き、クライアントだけで完結させる方式。
ランキングはメンバー各自が書き込む統計スナップショットを並べ替えるだけで、サーバーサイドのコードを持たない。
snapshot listener によるリアルタイム更新、オフラインキャッシュ、認証をマネージドで得られる。

- 利点:
  - 実装量が 3 案中もっとも少なく、登壇前に友人との実運用実績を作れる
  - 数人規模なら Spark プラン（無料）の範囲に収まる
  - ときどき六法での Firebase 利用経験を流用できる
- 欠点:
  - 訪問データ（実質的な行動履歴）が Google 管理下に置かれる
  - 発表素材としての技術的新規性は薄い

#### 案 B: 自前 Ktor サーバー + kotlinx.rpc + 共有 Kotlin モジュール

OneMoreCoffee は Ktor クライアントを既に利用しているため、Ktor サーバーを小さな VPS に立て、DTO を共有 Kotlin モジュールに置いて Kotlin end-to-end にする方式。
JetBrains の実験段階の RPC フレームワークである kotlinx.rpc を使えば、実験段階のライブラリを個人開発で先に踏むという自由 1 の物語にも接続する。

- 利点:
  - データ主権が完全に手元にある
  - Android カンファレンスの発表素材として独自性が高い
- 欠点:
  - TLS、ドメイン、稼働維持の運用負担を負う
  - プッシュ通知には結局 FCM（= Firebase プロジェクト）が必要で、管理対象が二重になる
  - 実装量は案 A の数倍と見込まれ、登壇準備期間（残り 2 ヶ月弱）と競合する

#### 案 C: バックエンドレス（既存サービスへの相乗り、ファイル交換）

専用バックエンドを持たない変種群。
共有 Google Drive フォルダに各自が JSONL を書いて相互にポーリングする、private リポジトリへの commit をフィード代わりにする、Discord webhook に投稿してフィード表示を Discord に任せる、近距離通信で会ったときだけ同期する、などを検討した。

- 利点:
  - 運用もコストもゼロ
  - 「検討して落とした案」として発表の 1 スライドになる面白さがある
- 欠点:
  - リアルタイム性がない（ポーリングまたは対面同期）
  - 認証と権限管理を他サービスから借用するため、トークン管理や利用規約との相性に難がある
  - どの変種もアプリ内での体験は妥協が大きい

### 3.3 比較と採用判断

| | 案 A: Firebase | 案 B: Ktor 自前 | 案 C: バックエンドレス |
|---|---|---|---|
| 実装量 | 小 | 中〜大 | 中 |
| 運用負担 | ほぼゼロ | あり | ゼロ |
| リアルタイム性 | ◎ | ○ | ✕ |
| データ主権 | △ | ◎ | ○ |
| 発表素材としての新規性 | △ | ◎ | ○ |

**案 A を採用する。**
決め手は登壇日（2026-09-01 から 03）までの残り時間である。
スライドの説得力は「実在の友人と実際に使っている」実績（本物のフィードのスクリーンショット、実データのランキング）に大きく依存するため、8 月中旬までに MVP の実運用を開始できる見込みが立つ案 A が優位となる。

案 B と案 C は捨てるのではなく、比較検討の過程ごと発表素材として本書に残す（§8）。
また §3.1 の導出データ原則により、サーバー上のデータは使い捨てられるため、登壇後に kotlinx.rpc への興味だけで案 B へ移行することも低コストで可能である。
この移行余地を保つため、Firebase 依存はモジュール境界で隔離する（§5.1）。

## 4. 機能設計

### 4.1 リーグ

数人の固定メンバーで使う前提から、1 対 1 のフレンド関係（申請と承認の管理が必要になる）ではなく、**リーグ**（招待コードで参加するグループ）を採用する。

- メンバーの誰かが「リーグを作成」すると、8 桁の招待コードが発行される
- 他のメンバーは招待コードの入力で参加する
- メンバーは表示名と絵文字アイコンを設定する（画像アップロード機能は作らない）
- リーグ内では全メンバーが互いのアクティビティと統計を見られる。ペア単位の可視性制御は作らない

データモデル上は複数リーグへの所属を許す構造とするが、UI は当面単一リーグ前提で作る。

招待コードの厳密なサーバーサイド検証は行わない。
検証には Cloud Functions（Blaze プランへの移行が必要）が要るため、コードを知っていることを事実上の入場券とする割り切りを採る（§5.3）。

### 4.2 ランキング

ランキングカードを 2 枚置く。

1. **総制覇数ランキング**：訪問済みユニーク店舗数（全国約 2,100 店中）。制覇率も併記する
2. **今月の新規制覇レース**：当月に初訪問したユニーク店舗数。毎月リセットされる

2 枚目を置く理由は、総数だけでは先行メンバーが固定化してランキングが動かなくなり、開く動機が失われるからである。
月次レースは後発メンバーにも毎月勝機があり、継続的にアプリを開く理由を作る。

同数の場合は表示名順で安定表示する。
月の境界は Asia/Tokyo 固定で判定する（利用者は全員日本在住のため）。
都道府県制覇数や Reserve 店舗数など他の軸は、統計スナップショットの項目追加だけで足せるため、将来拡張として温存する。

### 4.3 アクティビティフィード

イベント種別は 4 つに絞る。

| 種別 | 表示例 | 発生条件 |
|---|---|---|
| VISIT | 「A さんが 丸の内オアゾ店（東京都）を初訪問 ☕ 3 時間前」 | 未訪問店舗への訪問記録 |
| MILESTONE | 「A さんが 100 店舗制覇を達成 🎉」 | 総制覇数 50 刻み、都道府県コンプリート |
| BACKFILL | 「A さんが過去の訪問 287 店舗分を登録」 | 一括インポート（§4.4） |
| MEMBER_JOINED | 「A さんがリーグに参加」 | リーグ参加 |

フィードは投稿時刻の降順で表示する。
過去の日付を指定した手動記録（日記的な後追い入力）は、「7/1 の訪問」のように訪問日を明示して区別する。

**再訪はフィードに流さない。**
制覇支援アプリの主役は初訪問であり、再訪まで流すと常連店で毎回イベントが発生してノイズになるからである。
累計訪問数は統計スナップショットに含められるため、データとして失われるわけではない。

各イベントへの絵文字リアクションをフェーズ 2 で追加する（§7）。

### 4.4 インポートとフィードの共存（BACKFILL）

本体の My Starbucks インポート（本体設計書 §8.4）は、一度に数百店舗の訪問を登録しうる。
素朴に実装すると、初回連携でフィードに数百件の VISIT が一斉に流れる。

そこで、一度の同期で発生する新規訪問が 5 件を超える場合は、個別の VISIT イベントを発行せず、件数だけを持つ BACKFILL イベント 1 件に畳む。
統計スナップショットは件数によらず更新するため、ランキングには全件が即座に反映される。

### 4.5 共有粒度の検討経緯

訪問イベントは実質的に位置情報の履歴であるため、設計の初期段階では「店舗名は共有するが時刻はぼかす」案（訪問日を日付のみ持たせ、投稿も 3 時間遅延させる）を組み込んでいた。

しかし、利用者が互いに信頼する数人の友人に限られることを踏まえ、この防御は過剰と判断して撤回した。
「いまどこの店舗にいる」がそのまま伝わる生っぽさは、Swarm のようなチェックインサービスが示すとおり、close friends の間ではむしろ楽しさの源泉になる。

確定仕様は次のとおり。

- VISIT イベントは完全なタイムスタンプ（`visitedAt`）を持つ
- フィードでは「3 時間前」のような相対時刻で表示する（店舗詳細画面の最終訪問日の相対表示と一貫させる）
- 投稿は訪問記録の保存と同時に行う（意図的な遅延は入れない）
- 共有粒度の設定項目は作らない。ただしイベント発行を担う層を 1 箇所に集約し、将来ぼかしを入れる場合の変更点を局所化しておく

なお、ソーシャル機能そのものが完全オプトインであることが最終的な防波堤となる（§4.6）。

### 4.6 プライバシーと規約への整合

- ソーシャル機能は**完全オプトイン**とする。有効化しない限り、従来どおり一切の外部送信を行わない
- イベントに含めるのは `officialStoreId`、店舗名、都道府県、訪問日時のみとする。座標や営業時間などの店舗マスタ本体は送信せず、受信側の各端末が自分のローカルマスタから解決する。店舗名の焼き込みは、受信側のマスタに存在しない店舗（新店、閉店）を表示するための最小限の複製と位置付ける
- リーグ退出時には、自分の全イベントとメンバー情報をクライアント操作で削除できる
- 本体設計書 §3.3 の「外部送信は行わない」は改訂が必要になる（§6）

## 5. 技術設計

### 5.1 モジュール構成

Mitsubachi 流の core/feature 分割（本体の既存構成）を踏襲し、2 モジュールを新設する。

```
core/social      … Firestore クライアント、SocialRepository 実装、Hilt モジュール
feature/friends  … 「フレンド」タブ（フィード、ランキング、リーグ管理の UI）
```

インターフェース（`SocialRepository`）とモデル（`League`、`Member`、`ActivityEvent`）は、既存パターンに従い pure Kotlin の `core/domain` に置く。
Firebase SDK への依存は `core/social` に閉じ込め、既存の `core/data`（Room とスタバ API）には手を入れない。
この隔離は、案 B へ移行する場合に `core/social` の差し替えだけで済ませるための境界でもある（§3.3）。

ボトムナビゲーションは 4 タブから 5 タブ（マップ、リスト、統計、**フレンド**、設定）に変更する。
本体設計書 §10.1 で未決だった「通知フィードタブを足すか」の枠を、このタブが埋める。

### 5.2 Firestore スキーマ

```
inviteCodes/{code}                 → { leagueId }
leagues/{leagueId}                 → { name, createdBy, createdAt }
leagues/{leagueId}/members/{uid}   → { displayName, emoji, joinedAt,
                                       stats: { visitedStoreCount, prefectureCount,
                                                monthlyNewVisits: { "2026-07": 5 },
                                                updatedAt } }
leagues/{leagueId}/activities/{id} → { uid, type: VISIT | MILESTONE | BACKFILL | MEMBER_JOINED,
                                       officialStoreId?, storeName?, prefCode?,
                                       visitedAt?, count?, milestone?, createdAt }
```

設計の要点は次のとおり。

- **ランキングはサーバーで計算しない。**
  各メンバーが自分の Room から統計を導出して `members/{uid}.stats` に上書きし、クライアントは全員分（メンバー数 = 数件）を読んで並べ替えるだけとする。
  Firestore は集計が苦手な領域であり、通常は Cloud Functions によるマテリアライズが定石になるが、メンバー全員を信頼できる本機能では自己申告方式で足りる。
  これにより Cloud Functions（Blaze プラン）を回避し、Spark プランの無料枠に収まる
- ドキュメント ID による冪等化を行う。
  VISIT は `{uid}_{officialStoreId}`、MILESTONE は `{uid}_{種別}_{値}`、MEMBER_JOINED は `{uid}_joined` を ID とし、リトライや再送で同じイベントが重複しない構造にする
- 店舗名と都道府県はイベントに焼き込む（デノーマライズ）。
  受信側のマスタに存在しない新店や閉店店舗でも表示が壊れず、当時の店舗名が日記的に残る

### 5.3 セキュリティルール

方針レベルのルールを示す（正確な記述は実装時に詰める）。

```
inviteCodes/{code}   … get のみ許可（list は拒否し、コードの列挙を防ぐ）
leagues/{leagueId}   … read はメンバーのみ、create は認証済みなら可
  members/{uid}      … create/update は本人のみ、delete は本人またはリーグ作成者
  activities/{id}    … read はメンバーのみ、create/update/delete は本人のイベントのみ
                       （delete はリーグ作成者にも許可）
```

- 参加の検証は「招待コードを知っている者だけが `leagueId` に到達できる」ことに依存する soft security とする。
  厳密な検証には Cloud Functions が必要であり、友人数人の閉じた輪では過剰と判断した
- リーグ作成者に他メンバーのドキュメント削除を許すのは、端末紛失などで孤児化したメンバーの掃除役を作るためである（§5.5）。
  作成者権限の移譲機能は作らない。作成者の離脱は運用（リーグの作り直し）で対処する

### 5.4 同期フロー

```
訪問保存 (Room) ─→ 従来どおりここで完結（外部送信ゼロ）
      └─ ソーシャル有効時: PublishWorker を即時 enqueue
              ├─ 初訪問判定（Room の既存 Visit の有無）→ VISIT イベント書き込み
              ├─ マイルストーン判定 → 達成していれば MILESTONE イベント
              └─ 自分の stats を全 Visit から再計算して member doc を更新
インポート時: 新規 5 件超なら VISIT の代わりに BACKFILL 1 件 + stats 更新
フィード / ランキング画面: snapshot listener → Flow → Compose（画面表示中のみ attach）
```

即時投稿でも WorkManager を経由させるのは、遅延のためではなく、圏外や機内モードでの自動リトライを得るためである（訪問記録は地下街や移動中でも起きる）。
Firestore 自体のオフライン永続化も併用し、フィードは最後に取得した状態を常に表示できる。

訪問記録の削除（誤記録の取り消し）時は、冪等 ID で対応する VISIT イベントを特定して削除し、stats を再計算する。

### 5.5 認証とアカウントのライフサイクル

- **Firebase Anonymous Auth** を使う。アカウント作成 UI なしで、ソーシャル機能の初回有効化時に裏で uid が発行される
- 再インストールや機種変更では uid が変わる。
  その場合は招待コードで再参加し、BACKFILL として全履歴を再送すれば復元が完了する。
  Room が原本であるため、失われるものはない（§3.1 の導出データ原則がここで効く）。
  旧 uid の残骸はリーグ作成者が削除する
- Google アカウントへのリンクによる uid の永続化は、フェーズ 3 の拡張として経路だけ確保する

### 5.6 エッジケース

- 複数メンバーが同時刻に同じ店舗を訪問した場合：それぞれ別のイベントとして扱う。特別な処理はしない
- 店舗名の変更や閉店：イベントに焼き込んだ当時の名前で表示され続ける（日記的性質として意図どおり）
- 月間レースの月替わり：クライアントが現在月のキーで `monthlyNewVisits` を参照するだけで、サーバー側の処理はない
- Firestore 無料枠：読み取り 5 万件/日に対し、メンバー数人のフィードとランキングでは桁で余裕がある。ただし listener は画面表示中のみ attach し、常時接続はしない

### 5.7 シークレットと不正利用への備え

- リポジトリは public のため、`google-services.json` はコミットせず、既存の `secrets.defaults.properties` と同じ方式（gitignore + ローカル配置、CI では secret から注入）で扱う
- Firebase の構成情報は APK から抽出可能であり、第三者が本プロジェクトの Firestore に匿名認証で接続すること自体は防げない。
  データはセキュリティルール（§5.3）で保護されるが、野良リーグの作成など資源の無断利用は残る。
  Play Integrity による **App Check** をフェーズ 2 で導入し、正規ビルド以外からのアクセスを遮断する

### 5.8 テスト戦略

- 初訪問判定、マイルストーン判定、stats 導出、BACKFILL 閾値判定は pure Kotlin の関数に切り出し、既存の流儀で unit test を書く
- `SocialRepository` の Firestore 実装は **Firebase Emulator Suite** を相手にした統合テストとする（GitHub Actions では `firebase emulators:exec` で実行できる）
- ViewModel テストは既存パターンを踏襲し、Repository をフェイクに差し替える

## 7. 実装フェーズ

| フェーズ | 内容 | 目標時期 |
|---|---|---|
| 1 (MVP) | リーグ作成と参加、VISIT / BACKFILL / MEMBER_JOINED、フィード、総制覇数ランキング | 2026-08 中旬に友人との実運用を開始 |
| 2 | MILESTONE、月間レース、絵文字リアクション、App Check | 2026-08 下旬（スライド用スクリーンショットの確保まで） |
| 3 | FCM プッシュ通知（Blaze プラン化の判断込み）、Google アカウントリンク | 登壇後 |

フェーズ 3 のプッシュ通知を後回しにするのは、送信にサーバー資格情報が必要で、安全な実装には Cloud Functions（Blaze プラン）が要るためである。
フィードは snapshot listener でアプリ起動中はリアルタイムに更新されるため、MVP の体験としては通知なしでも成立する。

配布は友人への限定配布とし、Firebase App Distribution の招待制配布を第一候補にする。
public リポジトリの GitHub Releases への APK 添付は、事実上の公開配布になるため行わない。

## 8. 発表素材としての接続

本設計の過程と成果は、スライド構成設計書の次のスライドに接続できる。

- **S14「アイディアが実装に届くまで」（自由 2）**：本書に至るブレインストーミング（要件ヒアリング、3 案比較、設計確定）から実装計画、PR までの一連のログが、「アイディアを書き留めるだけで AI が計画を立て実装する」フローの具体例になる
- **S22 から S24（自由 4）**：ユーザー（自分と友人）との距離がゼロであることを利用した設計判断の実例。
  特に §4.5 の時刻ぼかし撤回は、「想定ユーザーに直接聞いて要件を変えた」エピソードとして、業務プロダクトとの対比で語れる
- **技術選定の比較（自由 3 の隣接素材）**：業務なら選定会議になる 3 方式比較を、個人開発では短時間で意思決定した事例。案 B（kotlinx.rpc）と案 C（バックエンドレス）は「検討して落とした案」として 1 スライドの価値がある
- **導出データ原則（§3.1）**：ローカルファーストのアプリにソーシャルを後付けする際のアーキテクチャ図として 1 枚になる

実運用が始まれば、実データのフィードとランキングのスクリーンショットを自由 4 の題材に追加できる。

## 9. オープンクエスチョン

実装計画の策定時に決める事項を残しておく。

1. Firestore のリージョン（asia-northeast1 を想定。数人規模では料金差は無視できる）
2. マイルストーンの刻み（50 で開始し、実運用の温度感で調整）
3. リーグ名と絵文字アイコンの入力仕様の詳細
4. Firebase Emulator Suite の CI 組み込みの詳細（既存 CI ワークフローとの統合方法）
5. インポートで取り込まれる `first_visit_date` が古い日付の場合、VISIT イベントの `visitedAt` に過去日時が入る。フィード表示（§4.3 の訪問日明示）で足りるか、実運用で確認する
